# 上游檔案零修改，建置時以 AST 腳本改寫為 runtime i18n

上游沒有 i18n 框架，約 1,000–1,500 條介面字串寫死在原始碼，且平均 2.7 天發一版。我們決定 fork 分支只「新增」檔案（腳本、語系檔、設定覆寫檔、workflow），不修改任何上游檔案；CI 建置時才由規則固定的 AST 腳本把字串包成 `__t()`（以英文原文為 key），並以覆寫方式套用 identifier、更新端點與版本號。這樣 merge 上游永不衝突、翻譯 PR 只含語系檔差異、上游的英文測試可原樣執行，同時保留語言切換與日後回饋上游的可能。

## Considered Options

- **字典就地改寫並 commit**（簡中 fork `transtone/angkorgit-zh` 的做法）：repo 內是中文原始碼，每次同步都要 `-X theirs` 後重套字典，測試也要跟著翻譯。該 fork 因壞譯文出貨、CI 轉紅而放棄全自動。
- **建置時直接替換成繁中**：同樣零修改，但安裝檔只有繁中、無法切換語言，也沒有可回饋上游的產物。
- **由人或 AI 改寫成語意 key 的 `t()` 並 commit**：key 可讀性好，但 AI 改寫結果不固定、無法在建置時重現，必須 commit，於是每版都有衝突，審稿人還得審程式碼。

## Consequences

- repo 內看不到 `__t()` 版原始碼；某個 tag 的建置結果取決於當時的腳本版本。
- 腳本認不出的字串會成為漏譯並阻擋發版，需補規則：規則寫在 `zh-tw/transform/rules.json`，在該上游版本的翻譯 PR 分支上補齊；發版 workflow 以 `apply.mjs --require-complete` 擋下沒有譯文的字串。
- 一句話被變數或行內元素切成多段、無法分段翻譯時，`rules.json` 的 `inject` 以錨點在建置時把那段原始碼換成整句；錨點必須剛好出現一次，上游改動該處時建置會失敗，而不是默默漏譯。
- 上游改動英文原文一個字就是新 key，舊譯文失效，需重新文案確認。
- 後端訊息（Rust 與 libgit2 回傳的文字）首版不翻譯：約三成帶動態參數，libgit2 原文數量無上限，要翻得靠第二套擷取腳本與執行時樣式比對，留待第二階段評估。畫面會出現「繁中句子加英文細節」的混排。CLI help 維持英文。
- `packages/core` 只被桌面 App 以原始碼形式打包，納入同一套腳本與漏譯檢查；其中的 AI 提示詞列入保留英文清單，設定搜尋的關鍵字則同時保留繁中與英文，需要一條專用規則。
- 回饋上游時，需另行把腳本的改寫結果產出成 PR；先在上游 issue #64 取得維護者同意。
